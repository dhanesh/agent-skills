# Open Knowledge Format (OKF) v0.1 — what this skill relies on

Spec: <https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md>
(Google Cloud, June 2026). The catalog produced here is a conformant OKF bundle, which is
what makes it readable by any other OKF consumer — including `okf-site-kit` in this repo,
which will render it as a browsable site with no extra work.

## The parts that matter here

| Spec area | What it says | How this skill uses it |
|---|---|---|
| §4 bundle | a directory of markdown files with YAML frontmatter, distributed as a git repo | the whole catalog |
| §4.1 frontmatter | `type` is required; producers may add their own keys, and consumers must tolerate unknown ones | every schema field beyond `type` is a producer extension |
| §6 index.md | reserved; a generated listing giving progressive disclosure over the tree | regenerated by every write mode |
| §7 log.md | reserved; the bundle's update history | appended on every creation/update/deprecation |
| §9 consumer rules | tolerate unknown types, unknown keys, missing optional fields and broken links | `validate` splits hard OKF conformance from soft catalog policy, and never rejects a bundle for any of those |

`README.md` and `CONTRIBUTING.md` at the bundle root are treated as human-facing furniture,
not concepts — they carry no frontmatter and are not loaded as documents.

## Where this skill goes beyond the spec

OKF says nothing about who may assert what. The whole authority model here — provider-owned
Capability, consumer-owned Verification, machine-owned Signal, and the commit-boundary
checks that enforce them — is a producer convention layered on top. Another OKF consumer
reading this bundle sees typed concepts and links; it will not enforce the ownership rules.
That is fine, and worth stating: the bundle is the interchange format, the rules live in
this tooling and in CI.

## Spec-update rule

OKF v0.1 is young and tooling is thin; expect to hand-author the markdown and own the
validator. Before assuming this skill is current:

1. Fetch the spec at the URL above and compare its declared version to `OKF_SPEC_VERSION`
   in `assets/catalog_core.py` (`0.1`).
2. If it has moved, read the changelog for changes to **required frontmatter**, the
   **reserved filenames**, or the **consumer tolerance rules** — those are the three places
   a version bump can invalidate what this tool emits.
3. Update `OKF_SPEC_VERSION`, then the writer and `validate()`, then add a fixture to
   `assets/test_okf_catalog.py` for the new shape *before* changing behaviour, so the change
   is measured rather than asserted.
