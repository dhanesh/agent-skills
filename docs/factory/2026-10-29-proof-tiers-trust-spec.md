# Spec: Proof-tier trust for the software factory

## Problem
Slices 1 and 1b of proof-tiered verification (`docs/factory/2026-10-22-proof-tiered-verification-spec.md`,
`docs/factory/2026-10-29-proof-tiers-gate-spec.md`) made the conductor hold a merge until each
gated clause has a proof record at the required tier, and froze contracts during a run. Two
independent advisors reviewed the result (Opus and Fable, 2026-10-29). Both said: ship it, but
the words `proved` and `property` now promise more than the checks behind them. The weak points
they found, each confirmed in the code:

1. `--tool` is a label. `record --tier proved --tool verus --cmd "true"` is accepted, because
   neither the recorder nor the conductor compares the tool with the command it ran.
2. `ASSURANCE:` takes the strongest tier any merged task recorded, at that task's own head
   (`assurance()` in `factory-conductor/assets/conductor.py`). A later task can change the
   proven code, and the line still says `proved`. `finish` re-runs verify commands, not proofs.
3. The head proof runs in the verifier's live worktree (`_run_proof(argv, root, ...)` in
   `cmd_record_tier`), while the mutant run uses a clean copy of the committed head.
4. A `proved` record can hide a Verus escape hatch (`assume(`, `admit(`, `external_body`). The
   first slice accepted this risk (its D11) on the promise of a reviewer search that never
   shipped.
5. At `min_tier: runtime`, a clause that no contract defines (`C99`) passes on runtime evidence.
6. "What the proof is worth" in `factory-conductor/SKILL.md` says nothing about tiers, so the
   one section a human reads to calibrate trust is silent on them.
7. The gate is proven on fixtures only: no feature of this repo has a contract.

## Users
- A human owner (Dhanesh) who reads `ASSURANCE:` lines from `conductor status` and in the run
  result, and must be able to trust each word in them without opening files.
- factory-conductor, which decides merges and writes the run result from these records.
- Verifier agents, which record proofs and need clear refusals when a record would overclaim.

## Terms
<!-- Extra section: ignored by spec_lint.py and spec_to_tasks.py. -->
- **Tiered plan:** a gated plan in which at least one task carries `min_tier` (`_tiered_plan`).
- **Run base:** `git merge-base <run branch> <verified head>` for the task being checked.
- **Verified head:** the commit `conductor verify` proved for a task.
- **Integration head:** the run-branch commit that `finish` re-runs every check on.
- **Runner table:** `RUNNERS` and `WRAPPERS` below, held as one literal copy in the recorder and one in the conductor, kept equal by a test.
- **Clean checkout:** a `git worktree add --detach` checkout of a commit, removed in `finally`. Unlike `git archive`, it ignores `export-ignore`.
- **Escape-hatch rule:** on a line the diff adds to a `.rs` file, `assume(` or `admit(` not preceded by an identifier character or by `::`, or `external_body` inside `#[verifier ...]` on the same line (regex `#\[verifier\b[^\]]*\bexternal_body\b`). Comments and strings are not skipped.

## Goals
- A tier record names a tool only when the command it ran is that tool's runner.
- Every head proof and every mutant proof runs in a clean checkout of a committed head.
- `ASSURANCE:` reports what held on the integration head, names that head, and the run result names the command behind each clause.
- A Rust change that adds a Verus escape hatch cannot merge in a tiered plan.
- A clause that the contract does not define cannot pass.
- The docs say plainly what each tier proves and what it does not.
- The run that builds this slice gates its own tasks on real contracts.

## Non-goals
- Tier-backend detection in verifier-installer (slice 3).
- A semantic check that a property tests the clause it names. The mutant check stays the floor.
- Proof generation, a `model` tier, or a floor on generated examples.
- Re-running runtime evidence (the verifier's app drive) at `finish`. Only proof records re-run.
- Showing `ASSURANCE:` in the PR body. It stays in `conductor status` and the run result.

## Constraints
- T1 [invariant]: A tier record exists, and counts, only when its argv passes `runner_matches(tool, argv)` on the runner table; the recorder and the conductor each hold a copy, kept equal by a test on a shared vector list.
- T2 [invariant]: The recorder runs the head proof and the mutant proof each in its own clean checkout of the committed head, and refuses a worktree with tracked changes.
- T3 [boundary]: Shipped tooling stays Python 3.10+ stdlib-only and offline; the target repo supplies the proof tools.
- T4 [invariant]: After `finish` re-runs the proofs, an `ASSURANCE:` line and the run result's `assurance` show a proof tier for a clause only when that proof held on the integration head, and name that head; `runtime` means the task's own runtime evidence at its verified head, which `finish` does not re-run.
- T5 [invariant]: A task in a tiered plan whose diff from its run base adds an escape hatch does not merge.
- T6 [invariant]: Every vendored copy of `verify_evidence.py` stays byte-identical to `verification-skill-forge/assets/verify_evidence.py`.
- T7 [boundary]: After every task, the per-skill gate (`make gate-skill`) of each skill the task changed passes.
- T8 [invariant]: The escape-hatch rule (Terms) is one rule, held by forge and the conductor and kept equal by one shared vector list.
- T9 [invariant]: One chance failure of a proof re-run at `finish` never claims a tier and never stops a run alone.
- T10 [invariant]: A clause counts at any tier only when its feature's `## Contract` at the verified head defines it.
- S1 [invariant]: A proof record counts only when the task's verifier, who is not its owner, recorded it; a `finish` re-run only lowers a clause's tier and records nothing.
- O1 [boundary]: A plan with no tier field merges and finishes exactly as it does today; the recorder's runner and dirty-tree refusals apply to every tier record.

## Tensions
- TN1 [trade_off]: Re-running every proof at `finish` makes the report true of the merged head, but it makes `finish` slower and needs the proof tools on the machine that runs it. (between: T4, T3; status: resolved; strategy: Prioritize; decision: D1)
- TN2 [trade_off]: A strict runner table refuses a real tool started through a wrapper such as `uv run` or `pnpm exec`. (between: T1, O1; status: resolved; strategy: Partition; decision: D7)
- TN3 [trade_off]: Property tools pick new random inputs on each run, so a re-run at `finish` can fail by chance. (between: T4, T9; status: resolved; strategy: Partition; decision: D8)
- TN4 [hidden_dependency]: A mutant patch made at one task's head may not apply on the integration head after later tasks change the file. (between: T4, T9; status: resolved; strategy: Transform; decision: D9)
- TN5 [hidden_dependency]: Every existing test, fixture, recipe and A/B probe fakes a proof tool as `python tool.py` and writes features with no contract, so T1 and T10 break them unless the same task migrates them. (between: T1, T10, T7; status: resolved; strategy: Transform; decision: D12)

## Residual risks
- A property can still pass its mutant without testing the clause it names. The mutant proves
  the command can fail, not that it fails for the right reason.
- A shell-capable agent can still forge a record by hand. Merge to `main` stays with a human.
- The runner table can be bypassed by a runner that the table lists but that runs something
  else (`pytest` with a plugin that always passes). The reviewer still reads the diff.
- Re-running proofs at `finish` needs the proof tools on that machine; without them clauses report
  `runtime` (D13). `finish` has no total time bound beyond each record's own timeout.
- A clean checkout has no build cache (`target/`, `node_modules`, `.venv`), so a re-run can be slow,
  and `npx` or `uv run` can try the network, against T3. The repo's own tasks use no such tool.
- A runner the table lists can still run something else (`pytest` with a plugin that always
  passes, or a `yarn` script alias). The reviewer still reads the diff.
- A multi-line `#[verifier(...)]` attribute escapes the line-based escape-hatch rule.
