# Spec: project-atlas — index every project on a machine into a durable, searchable, cloud-replicated SQLite database

## Problem

A developer machine accumulates hundreds of project directories across `~/src`, `~/work`,
`~/Downloads`, and half-remembered one-off clones. Answering "where is that repo that used
the Stripe webhook?", "which of my checkouts still point at the old GitLab remote?", or
"what have I not touched in a year?" today means `find` plus guesswork, and the answer dies
with the machine — a reinstall or a lost laptop takes the map with it. The pieces to fix
this are all commodity (SQLite, FTS5, Litestream, S3/R2), but wiring them into something an
agent can stand up in one pass is the missing part.

## Users

- **The developer who owns the machine** — wants one command that finds a project by name,
  language, remote, or a phrase from its README, and wants that index to survive the
  machine.
- **A coding agent working on that machine** — wants a queryable inventory of local projects
  so it can locate the right checkout without walking the whole filesystem.
- **The same developer on a new machine** — wants to restore the index from object storage
  and immediately see what existed before, and to pick up an agent session that was left
  half-finished on the old one.

## Goals

- One scan command turns a set of filesystem roots into rows in a SQLite database, with
  git and toolchain metadata attached.
- Full-text search over project READMEs, docs, and paths from the command line.
- Agent sessions — the chat transcript plus the side state a resume needs — captured into
  the same database, searchable, and replayable onto a different machine whose paths differ.
- Continuous replication of that database to S3, Cloudflare R2, or any S3-compatible
  bucket via Litestream, with a documented, one-command restore.
- The generated Litestream configuration matches the Litestream 0.5.x schema and the
  target provider's known constraints, so it runs without hand-editing.

## Non-goals

- Not a code-search engine over full source trees — the index covers metadata, paths, and
  documentation text, not every source file.
- Not a Cloudflare Durable Object / Worker deployment. The durable store is a local SQLite
  file replicated to object storage; serving it from an edge runtime is out of scope.
- Not a background daemon or file-system watcher. Scans are invoked (by the user, a cron
  entry, or an agent); only Litestream runs continuously.
- Not a package manager, dependency auditor, or build tool. The skill records what
  toolchain markers exist, and does not run them.
- Not a secrets store. Credentials stay in the environment; the skill never writes them to
  disk.
- Not an account or credential sync. Session capture carries conversations and working
  state, never the agent's account identity or login tokens.
- Not a live multi-machine session handoff. Resume is restore-then-continue after a sync,
  not two machines writing one conversation at once.

## Requirements

- R1: `atlas scan` must identify a directory as a project root when it contains a `.git`
  directory or a recognised toolchain manifest, and must not descend below a directory
  named in the prune list (`.git`, `node_modules`, `.venv`, `venv`, `target`, `dist`,
  `build`, `.tox`, `vendor`, `__pycache__`). [where: project-atlas/assets/atlas.py]
- R2: A second `atlas scan` over unchanged roots must leave the number of rows in the
  `projects` table unchanged, updating only `last_scanned`. [where: project-atlas/assets/atlas.py]
- R3: For a project root that is a git working tree, `atlas scan` must record its origin
  remote URL, current branch, HEAD commit id, and HEAD commit timestamp; for every project
  root it must record the absolute path, project name, detected languages, and detected
  toolchain markers. [where: project-atlas/assets/atlas.py]
- R4: When a previously indexed project path no longer exists, `atlas scan` must retain its
  row and set `missing_since`, and must not delete the row. [where: project-atlas/assets/atlas.py]
- R5: Every connection `atlas` opens against the index must set `journal_mode=WAL` and must
  fail with a non-zero exit code if the resulting mode is not `wal`, because Litestream
  replicates from the WAL. [where: project-atlas/assets/atlas.py]
- R6: `atlas search` must use an FTS5 index when the SQLite build provides FTS5, and must
  fall back to a `LIKE` scan producing the same output protocol and exit code 0 when FTS5
  is absent. [where: project-atlas/assets/atlas.py]
- R7: The searchable document for a project must include its path, name, and the text of
  its README and top-level docs, and must index at most 65536 bytes of text per project so
  a large docs tree cannot dominate the database. [where: project-atlas/assets/atlas.py]
- R8: `atlas litestream-config` must emit the Litestream 0.5.x singular `replica:` mapping
  under each `dbs:` entry, and must not emit the deprecated `replicas:` list.
  [where: project-atlas/assets/atlas.py]
- R9: When the target is Cloudflare R2, the generated replica URL must carry an `endpoint`
  whose value begins with `https://`, because Litestream's R2 provider detection keys on
  the scheme. [where: project-atlas/assets/atlas.py]
- R10: The generated configuration must set an explicit `sync-interval` rather than
  inheriting Litestream's 1s default. [where: project-atlas/assets/atlas.py]
- R11: The generated configuration must reference credentials as environment-variable
  expansions and must not contain a literal access key or secret value.
  [where: project-atlas/assets/atlas.py]
- R12: `atlas doctor` must report FTS5 availability, the index journal mode, and whether a
  `litestream` binary is on `PATH`, and must exit non-zero when a capability the configured
  mode requires is missing. [where: project-atlas/assets/atlas.py]
- R13: `atlas litestream-config` must also print the exact `litestream restore` command for
  the configured replica, so recovery does not require reading the Litestream manual.
  [where: project-atlas/assets/atlas.py]
- R14: The shipped tooling must run on python3 with the standard library only, and must
  perform no network access during `scan`, `search`, `stats`, or `doctor`.
  [where: project-atlas/assets/]
- R15: The skill must ship a stdlib unit suite and an `eval/run_eval.py` outcome eval whose
  checks include at least 1 negative fixture that the grader rejects.
  [where: project-atlas/eval/run_eval.py]
- R16: `atlas sessions ingest` must record, for each discovered agent session, its session
  id, working directory, git branch, CLI version, first and last timestamps, user and
  assistant turn counts, and the sha256 of the original transcript bytes.
  [where: project-atlas/assets/atlas.py]
- R17: Every record in a captured transcript must be stored verbatim as its own row in
  document order, so that a session whose record types the tool does not recognise is still
  captured in full. [where: project-atlas/assets/sessions.py]
- R18: Reconstructing an unredacted capture must produce a byte-for-byte copy of the
  original transcript, and the restore must report which verification it achieved.
  [where: project-atlas/assets/sessions.py]
- R19: `atlas sessions ingest` must replace a previously captured session's events rather
  than append to them, so a rewound transcript does not leave a mixture of two histories.
  [where: project-atlas/assets/atlas.py]
- R20: Session capture must redact credential-shaped strings from transcripts and side
  state by default, record a per-kind count of what was removed, and require an explicit
  `--no-redact` flag (which must print a warning) to store them verbatim.
  [where: project-atlas/assets/sessions.py]
- R21: Session capture must never read the agent's account configuration file, and must
  exclude shell snapshots unless `--include-shell-snapshots` is passed.
  [where: project-atlas/assets/sessions.py]
- R22: `atlas sessions restore` must write the transcript to the target machine's project
  directory computed from the target working directory, rewriting the `cwd` field of every
  record, and must also restore the session's task state.
  [where: project-atlas/assets/atlas.py]
- R23: `atlas sessions restore` must refuse to run when the stored parent chain has a
  missing link, when the target file exists and `--force` was not passed, or when the
  capture was redacted and `--allow-redacted` was not passed.
  [where: project-atlas/assets/atlas.py]
- R24: Captured chats must be full-text searchable through `atlas sessions search`, using
  FTS5 where available and the same LIKE fallback contract as project search.
  [where: project-atlas/assets/atlas.py]

## Acceptance criteria

- R1: Build a fixture tree with a git repo, a `pyproject.toml` project, and a
  `node_modules/inner-pkg/package.json`; `atlas scan` on it reports exactly 2 projects and
  the `node_modules` path appears in no row.
- R2: Run `atlas scan` twice on the same fixture; `SELECT count(*) FROM projects` returns
  the same number both times and the second run's `last_scanned` is >= the first's.
- R3: On a fixture git repo with an origin remote and one commit, the project's row has
  non-empty `git_remote`, `git_branch`, `git_head`, `git_head_at`, `languages`, and
  `toolchains` columns.
- R4: Scan a fixture, delete one project directory, scan again; that project's row still
  exists and its `missing_since` column is non-null.
- R5: After any `atlas` command touches the index, `PRAGMA journal_mode` on the file
  returns `wal`; a read-only directory that forces rollback mode makes the command exit
  non-zero.
- R6: `atlas search stripe` returns the seeded project on a build with FTS5; with FTS5
  forced off the same query returns the same project id and exits 0.
- R7: Seed a project whose README is 200000 bytes; the stored document for that project is
  at most 65536 bytes and still matches a term from its first 1000 bytes.
- R8: `atlas litestream-config --target r2 ...` output parsed as YAML has
  `dbs[0].replica` as a mapping and has no `dbs[0].replicas` key.
- R9: The same output's `dbs[0].replica.url` contains `endpoint=https://` and the
  configured account host.
- R10: The same output contains a `sync-interval:` key with a non-empty value.
- R11: Running the generator with `AWS_SECRET_ACCESS_KEY` set in the environment produces
  output that does not contain that value, and does contain `${` expansions for the key id
  and secret.
- R12: `atlas doctor --json` emits an object with `fts5`, `journal_mode`, and `litestream`
  keys; invoking it with `--require litestream` on a PATH without the binary exits 1.
- R13: `atlas litestream-config` output includes a line beginning `litestream restore`
  containing the same replica URL as the config body.
- R14: `grep -rE '^(import|from) ' project-atlas/assets/*.py` lists only standard-library
  modules, and the eval and unit suites pass with networking unavailable.
- R15: `python3 project-atlas/eval/run_eval.py` prints `EVAL_RESULT: PASS (n/n checks)`,
  exits 0, and its output includes at least one check whose name marks it a negative
  fixture.
- R16: After ingesting a fixture agent home, the session's row has the fixture's cwd,
  branch `main`, version `2.1.0`, turn counts matching the fixture, and a 64-character
  `transcript_sha256`.
- R17: A fixture transcript of 3 records — one of them a type the tool has no special
  handling for — yields exactly 3 `session_events` rows in seq order 0,1,2.
- R18: Ingest a fixture with `--no-redact`, restore it, and `cmp` the restored file against
  the original: identical, and the command's output contains `verify=sha256-exact`.
- R19: Ingest a 2-record transcript, truncate it to 1 record, ingest again; the session has
  exactly 1 event row.
- R20: Ingest a transcript containing a planted `DB_PASSWORD=` value; that value appears
  nowhere in `sqlite3 <db> .dump`, `[REDACTED:` does, and the row's `redacted` column is 1.
  Re-ingesting with `--no-redact` prints a warning on stderr and sets `redacted` to 0.
- R21: With an account-config file and a shell snapshot present in the fixture, a default
  ingest produces a dump containing neither `oauthAccount` nor the snapshot's planted
  value, and no artifact row of kind `shell-snapshot`.
- R22: Restore with `--cwd /Users/dev/payments` writes
  `projects/-Users-dev-payments/<id>.jsonl` under the target home, every record's `cwd`
  reads `/Users/dev/payments`, and `tasks/<id>/1.json` exists.
- R23: Each of the three refusals exits 1 with a message naming the cause: deleting the
  first event row yields `parent chain`; a second restore without `--force` yields
  `--force`; restoring a redacted capture without `--allow-redacted` yields `redaction`.
- R24: `atlas sessions search webhook --json` returns the fixture session id, and the same
  query with `--no-fts` exits 0 reporting `engine=like`.

## Open questions

- Should a future version push the index into a Cloudflare Durable Object so a Worker can
  serve queries? Deferred: the user scoped this build to local SQLite + Litestream.
- Whether to add optional full-source FTS behind a flag once the docs-only index proves out
  in daily use.
