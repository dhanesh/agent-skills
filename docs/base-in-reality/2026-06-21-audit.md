## Executive summary

Audited the factual/normative claims of all five skills in this repo (the techniques, standards, APIs, tool behaviours, and research each one asserts) against authoritative, fetched sources — ~59 falsifiable claims, each verdict grounded in ≥1 source pulled this session and candidate findings passed through an adversarial refutation gate. **Every skill is substantially based in reality: zero fabricated authorities, zero invented APIs/commands, zero mischaracterized citations.** Findings are 1 high + 2 medium + 2 low (a sixth, the debate counts, was initially UNCONFIRMED and later CONFIRMED against the paper body — see below), and all are *currency/precision* issues (an API's policy changed, a version moved, a unit slipped) rather than anything made-up. The single most important issue: **context-hygiene-kit's hook `timeout` values are in milliseconds but Claude Code interprets `timeout` in seconds**, so a wedged hook would hang a turn for ~4 hours instead of 15s. Notably, the `crafting-self-prompting-loops` research grounding added earlier verified clean — all ~16 cited arXiv IDs resolve to the right paper and the attributed findings match the sources (0 wrong IDs, 0 mischaracterizations).

## Findings

### [high] DEVIATION — Hook `timeout` values are in ms, but Claude Code reads seconds

- **Claim:** The kit's hook timeouts (`15000`, `30000`) bound a hung hook to 15 s / 30 s.
- **Location:** `context-hygiene-kit/assets/settings.hooks.json:11,23,35`
- **Layer:** arch
- **Assessment:** Claude Code interprets the hook `timeout` field in **seconds**, so `15000`/`30000` request ~4.2 h / ~8.3 h, not 15 s / 30 s. The hooks still run, but the kit's stated "never block the lifecycle" guarantee is defeated: a wedged `stop.sh` would hang the turn for hours. Upheld by an adversarial re-check against the official docs.
- **Citations:**
  - Claude Code — Hooks reference — https://code.claude.com/docs/en/hooks — "`timeout` … Seconds before canceling. Defaults: 600 for `command`, `http`, and `mcp_tool`; 30 for `prompt`; 60 for `agent`."
- **Recommended fix:** Change `15000` → `15` and the two `30000` → `30` in `settings.hooks.json`.

### [medium] DEVIATION — Semantic Scholar routed as a preferred keyless source, but unauthenticated access 429s

- **Claim:** Semantic Scholar is a preferred keyless API ("keyless APIs … preferred for speed and reproducibility"), and is the *primary* routed source for security/crypto, algorithms, distributed-systems, and ML claims.
- **Location:** `base-in-reality/references/source-routing.md:3,10,13-14`; `base-in-reality/assets/fetch_sources.py:32-38`
- **Layer:** arch
- **Assessment:** Running the bundled helper live, **4/4 unauthenticated Semantic Scholar queries returned `HTTP Error 429`.** S2 is technically keyless but its shared unauthenticated pool is aggressively throttled, and S2's own docs recommend a key on every request. As routed today, the skill's highest-priority source for several domains fails in practice.
- **Citations:**
  - Semantic Scholar — Academic Graph API — https://www.semanticscholar.org/product/api — "we recommend including your API key with every request"; live runs of `fetch_sources.py --source semanticscholar` → `{"error":"HTTP Error 429"}` (×4)
- **Recommended fix:** Add an optional `S2_API_KEY` env → `x-api-key` header in `fetch_sources.py`; in `source-routing.md`, demote S2 to secondary behind arXiv/OpenAlex and note it may 429 without a key.

### [medium] OUTDATED — OpenAlex described as keyless; it is now a metered freemium requiring a key, polite pool removed

- **Claim:** OpenAlex is an unconditionally-keyless API, used via the "polite pool" with a `mailto` contact.
- **Location:** `base-in-reality/references/source-routing.md:3,12,15`; `base-in-reality/references/domains.md:22`
- **Layer:** arch
- **Assessment:** As of 2026-02-13 OpenAlex became a metered freemium: API calls require a key for sustained use, exceeding the small free allowance returns `429`, and the polite pool + `mailto` parameter were **explicitly removed.** Low-volume calls still succeed (confirmed live at `--limit 1`), so this is currency drift, not a fabrication. (OpenAlex's own docs disagree on the exact no-key daily allowance — $0.10/day vs $0.01/day across two official pages — so treat the figure as approximate; the key-required + polite-pool-killed substance is firmly sourced.)
- **Citations:**
  - OpenAlex announcement — https://groups.google.com/g/openalex-users/c/rI1GIAySpVQ — "No more polite pool! No more email parameter in your calls… API calls will require a key starting one month from today (Feb 13)."
  - OpenAlex — Authentication & rate limits — https://developers.openalex.org/api-reference/authentication — "If you exceed your daily limit or make more than 100 requests per second, you'll get `429 Too Many Requests` errors."
- **Recommended fix:** Stop describing OpenAlex as unconditionally keyless; document the free key + metering and the removal of the polite pool; add optional key support to the helper.

### [low] DEVIATION — Helper sets a User-Agent but does not join the CrossRef polite pool

- **Claim:** The helper follows polite-pool etiquette via its User-Agent.
- **Location:** `base-in-reality/references/source-routing.md:62-64`; `base-in-reality/assets/fetch_sources.py:163-166`
- **Layer:** arch
- **Assessment:** CrossRef's polite pool requires a `mailto` (as a query param or inside the UA). The helper's UA carries a GitHub URL but no `mailto:`, so requests land in CrossRef's public pool. (OpenAlex's polite pool no longer exists — see above — so this now applies to CrossRef only.)
- **Citations:**
  - CrossRef — REST API access & authentication — https://www.crossref.org/documentation/retrieve-metadata/rest-api/access-and-authentication/ — polite pool keyed on a `mailto` contact in the request.
- **Recommended fix:** Add a `mailto:` to the UA and a `mailto` param for CrossRef, or drop the polite-pool implication from the docs.

### [low] DEVIATION → FIXED (build-verified) — Pinned Astro/Starlight dependencies trailed current releases

- **Claim:** Scaffold pinned `astro ^5.16.0` and `@astrojs/starlight ^0.36.0`.
- **Location:** `starlight-handbook-kit/assets/templates/scaffold/package.json`
- **Layer:** arch
- **Correction to an earlier note:** A prior pass deferred this finding, suspecting the version data was *fabricated* (the odd-looking `@astrojs/markdown-satteri` / "Sätteri processor"). **That suspicion was wrong** — GitHub's authenticated API confirms `@astrojs/markdown-satteri` is a *real* Astro package (it has real release tags, e.g. `0.3.1-beta.2`), Astro 6 is real (6.4.8 stable, 7.0 in beta), and Starlight 0.40.0 is real. The skepticism over-fired into a false positive; the npm data was correct all along. Lesson logged: an unfamiliar-looking name is not evidence of fabrication — corroborate before calling it fake.
- **Assessment:** Bumped to the current stable set, sourced from GitHub (not the npm mirror) and matching the canonical Starlight 0.40 starter (`examples/basics` pins `astro ^6.4.5`, `@astrojs/starlight ^0.40.0`): `@astrojs/react ^5.0.7`, `@astrojs/starlight ^0.40.0`, `astro ^6.4.5`. **Verified with a real build:** `npm install` (resolved astro@6.4.8 / starlight@0.40.0 / react@5.0.7, all peers satisfied) + `astro build` → `Complete!`, 5 pages + pagefind + sitemap. One deprecation warning remains (Astro 6 deprecated `markdown.rehypePlugins`, used by the scaffold's base-link plugin — still works on 6, should migrate to the `@astrojs/markdown-remark` unified API before Astro 7). Tracked as a follow-up.
- **Citations:**
  - GitHub release tags (authenticated API) — `withastro/starlight@0.40.0`, `withastro/astro@6.4.8`, `@astrojs/markdown-satteri@0.3.1-beta.2`
  - Canonical starter — `withastro/starlight` `examples/basics/package.json` @ `@astrojs/starlight@0.40.0` — `"astro": "^6.4.5"`, `"@astrojs/starlight": "^0.40.0"`
- **Recommended fix:** Done — bumped and build-verified. Follow-up: migrate `markdown.rehypePlugins` to the Astro 6 `unified()` API before Astro 7.
