## Executive summary

40 falsifiable claims were extracted (8 per skill) and verified against authoritative sources;
**71 distinct sources were fetched in-session** (arXiv, official API docs, W3C/WCAG/APG, OWASP,
NIST/IETF RFCs, tmux/systemd man pages). After the adversarial refutation pass, **6 findings
survived: 1 VIOLATION and 5 DEVIATIONs**; **13 candidate findings were downgraded to UNCONFIRMED**
when ≥2 of 3 refuters defeated them (mostly citation over-application), and the remaining 21 claims
were grounded as *accurate* (no contradiction found).

The signal concentrates in **`tmux-agent-herdr-lite`'s status classifier** (`scripts/agent-status-scan`):
the one VIOLATION is that `classify()` matches stale `blocked`/`error`/`done` regexes against the
**visible pane buffer before** checking whether the pane actually changed, and captures only the
viewport — so a scrolled-in token pins a wrong status independent of activity. The single most
important *correctness-adjacent* issue elsewhere is `context-hygiene-kit`'s `<data>…</data>` fence
being presented as *the* prompt-injection defense when it is a soft, escapable delimiter (the
load-bearing control — harvest-side exclusion of tool output — is sound; the framing overstates the
fence). None of the findings are security-critical or financial-correctness failures.

### [high] VIOLATION — `agent-status-scan` matches stale buffer regexes before checking pane activity, over only the visible viewport

- **Claim:** `classify()` runs `blocked`/`error`/`done` regexes *before* the buffer-change (hash) check,
  so a stale visible-pane match (e.g. a scrolled-in `blocked`, `429`, or `done`) pins the status
  regardless of activity; and `tmux capture-pane -p -J` reads only the **visible** buffer, making
  detection order- and viewport-dependent.
- **Location:** `tmux-agent-herdr-lite/scripts/agent-status-scan:41-61` (and the `capture()` call at `:37-39`)
- **Layer:** algo
- **Assessment:** Verified true in code: `classify()` evaluates `blocked_patterns` (`:43-44`),
  `error_patterns` (`:45-46`), and `done_patterns` (`:47-48`) and short-circuits *before* the
  SHA-256 hash/activity check (`:49-53`), and the loose anchors are real (`\bdone\b` matches
  "not done yet"; `\b429\b` matches any occurrence). The `tmux capture-pane -p -J` call (`:38`) passes
  no `-S`/`-E` scrollback range, so per the tmux(1) manual it captures **only the visible contents** —
  detection therefore depends on scroll position. The refutation pass confirmed correctness *and*
  citation-applicability (2 of 3 lenses upheld it); only the severity lens dissented, arguing the blast
  radius is cosmetic and self-correcting (the offending token scrolls out next scan). Verdict stands as
  VIOLATION; treat the **high severity as contested** — for a local, advisory-only dashboard label with
  no automated action, medium is defensible.
- **Citations:**
  - tmux capture-pane manual — https://man.openbsd.org/tmux.1 — "The default is to capture only the visible contents of the pane."
- **Recommended fix:** Check buffer-change/idle *first* and classify `working` when the pane changed
  recently, only falling to `blocked`/`done` when quiescent; scan only the **tail** (last non-empty
  line / prompt region), not the whole scrollback; anchor on the `AGENT_STATUS:` sentinel on the last
  line and treat loose word patterns as advisory tie-breakers.

### [high] DEVIATION — crash/`error` state is folded into `blocked`, and the dashboard's `error` state is never emitted

- **Claim:** `error_patterns` (traceback, uncaught exception, command failed, `exit_code!=0`) return
  `'blocked'` rather than a distinct `error`/`✖` state, conflating a crashed agent with one awaiting
  input — even though the dashboard reserves `icons['error']='✖'` and `order['error']=1`.
- **Location:** `tmux-agent-herdr-lite/scripts/agent-status-scan:28,45-46`; contradicted by `agent-dashboard:15-16`
- **Layer:** arch
- **Assessment:** Factually accurate: `error_patterns` are folded into `return 'blocked'`, evaluated
  *after* `blocked_patterns`, and no scanner path ever emits `'error'` (and `agent-status-summary:22`
  omits it from its icon map) — a dead first-class UI state. The refutation pass upheld correctness but
  flagged the systemd `failed`-vs-`inactive` citation as analogized rather than binding, and noted both
  conditions already route to the same "look at this pane" affordance and sort to the top (`blocked`
  has `order` 0). Verdict survives as DEVIATION; **severity is contested** (label-precision/consistency
  gap, arguably medium).
- **Citations:**
  - systemd.unit(5) — Linux manual page — https://www.man7.org/linux/man-pages/man5/systemd.unit.5.html — the `failed` vs `inactive` distinction (a failed unit needs explicit operator action, not the same affordance as a quiescent one).
- **Recommended fix:** In `classify()`, return `'error'` for `error_patterns` matches and evaluate
  `error_patterns` **before** `blocked_patterns` so a real crash isn't masked by an incidental
  `permission denied`/`429` substring. Wire an `error` jump target into `agent-jump`/`agent-menu` and
  add the missing `error` icon to `agent-status-summary` so a crashed agent is reachable distinctly.

### [medium] DEVIATION — `<data>…</data>` fence presented as *the* prompt-injection defense is a soft, escapable delimiter

- **Claim:** Two-channel trust boundary harvests only user+assistant "trusted" text (tool_result/tool_use
  never ingested) and wraps untrusted-provenance content in `<data>…</data>` fences so a downstream
  model treats it as data, not instructions — presented as **the** prompt-injection defense. The fence
  is an unescaped delimiter, bypassable when untrusted content itself contains `</data>`.
- **Location:** `context-hygiene-kit/SKILL.md:63`; `assets/context_ledger.py:51-57,245-250,259-260`; `assets/harvest.py:21-26`
- **Layer:** arch
- **Assessment:** The refutation pass upheld this on all three lenses (0 refuters). The load-bearing
  control — harvest-side exclusion of tool output and the requirement that markers start the line — is
  sound and tested; the issue is the *framing*: a soft, unescaped `<data>` fence is OWASP's
  "segregate/denote external content" best-effort delimiter, **not** a complete boundary, and untrusted
  text containing `</data>` lands outside the fence.
- **Citations:**
  - LLM01:2025 Prompt Injection — OWASP Gen AI Security Project — https://genai.owasp.org/llmrisk/llm01-prompt-injection/
  - OWASP LLM01 (2023-24) — delimiters & external-content segregation — https://genai.owasp.org/llmrisk2023-24/llm01-24-prompt-injection/
  - The Dual LLM pattern (Simon Willison) — https://simonwillison.net/2023/Apr/25/dual-llm-pattern/
- **Recommended fix:** (1) Sanitize the delimiter in `to_digest()` — strip/escape any `</data>`/`<data>`
  in untrusted `card.content` before wrapping, with a test asserting an injected `</data>` cannot
  produce a second closing fence. (2) Reframe `SKILL.md:63` from "THE prompt-injection defense" to a
  layered statement: the harvest-side exclusion is the load-bearing control; the fence is a best-effort
  soft delimiter that is not foolproof. If untrusted content must ever reach a tool-capable downstream
  model, prefer the dual-LLM/quarantine pattern.

### [low] DEVIATION — refutation aggregator is a plain 2-of-3 majority vote over a same-model ensemble

- **Claim:** The adversarial refutation protocol spawns ≥3 refuters across distinct lenses (correctness,
  citation-applicability, severity), each defaulting to `refuted=true` under uncertainty, and downgrades
  to UNCONFIRMED on ≥2-of-3 refute.
- **Location:** `base-in-reality/references/verdict-rubric.md:28-36`
- **Layer:** algo (self-audit of this skill)
- **Assessment:** The description faithfully matches the rubric, and ensemble/multi-judge verification is
  literature-grounded. DEVIATION because the *specific aggregator* — a plain majority vote over a small
  odd ensemble that shares one underlying model — is the baseline recent work flags as brittle under
  "confabulation consensus" (correlated bias). Distinct lenses partially decorrelate the refuters
  (good), but not fully. (1 of 3 refuters dissented; verdict survives.)
- **Citations:**
  - Harnessing Multiple LLMs: A Survey on LLM Ensemble — arXiv:2502.18036 (abstract_only)
  - Auto-Prompt Ensemble for LLM Judge — arXiv:2510.06538 (abstract_only)
  - Auditing Multi-Agent LLM Reasoning Trees Outperforms Majority Vote — arXiv:2602.09341
  - MAD-Fact: Multi-Agent Debate for Long-Form Factuality — arXiv:2510.22967 (abstract_only)
- **Recommended fix:** State explicitly that refuters must be decorrelated (distinct lenses minimum,
  ideally distinct models) to justify treating votes as near-independent; consider a unanimity
  requirement for high-severity verdicts or evidence-weighted adjudication rather than a raw 2-of-3 vote;
  cite the false-positive-control rationale so the design choice is auditable.

### [low] DEVIATION — MAST failure-mode percentages are misreported in the literature reference

- **Claim:** The MAST reference cites 14 failure modes in 3 categories with distribution 41.8% /
  36.9% / 21.3% (κ=0.88), and that tactical prompt/orchestration tweaks recovered only 9.4–15.6%.
- **Location:** `crafting-self-prompting-loops/references/literature.md:36`
- **Layer:** arch (filed as algo — the `arch` enum was rejected by a harness validation quirk during extraction)
- **Assessment:** Three of four cited facts are verbatim-grounded in the fetched paper (14 modes / 3
  categories; κ=0.88; +9.4 and +15.6 point ChatDev gains that remain insufficient). The category
  distribution **41.8 / 36.9 / 21.3 appears in neither v1 nor v3** — the paper's conversation-stage
  split is 37.17 / 31.41 / 31.41 (Pre/Execution/Post). DEVIATION because one secondary statistic is
  fabricated/misattributed while the directional claim holds (0 refuters; verdict survives).
- **Citations:**
  - Why Do Multi-Agent LLM Systems Fail? (MAST), Cemri et al. — arXiv:2503.13657 (abstract_only)
  - MAST v1 full PDF, Fig. 2 conversation-stage distribution — https://arxiv.org/pdf/2503.13657v1
- **Recommended fix:** Replace `41.8/36.9/21.3` with the paper's actual stage split (37.2/31.4/31.4,
  relabeled as conversation-stage frequencies) **or** drop the specific percentages and state that
  failures spread across system-design, inter-agent, and verification categories with no single dominant
  bucket. Soften the derived "budget ~40/37/21" design rule to "spread design effort across all three;
  don't over-index on a smarter model."

### [low] DEVIATION — redundant `aria-valuemin/max/now` on a native range input (and the gate asserting them)

- **Claim:** `TradeoffSlider` uses a native `<input type="range">` exposing `aria-valuemin/max/now/text`,
  and the a11y gate asserts `aria-valuenow` presence.
- **Location:** `starlight-handbook-kit/assets/templates/scaffold/src/components/TradeoffSlider.tsx:62-75`; gate at `scripts/check-a11y-nojs.mjs:53`
- **Layer:** algo
- **Assessment:** The core decision (native `<input type="range">` over a custom div slider) is
  authoritatively correct — keep it. But `aria-valuemin/valuemax/valuenow` are **redundant** on a native
  range input: native `min`/`max`/`value` already expose those semantics, ARIA-in-HTML says authors
  SHOULD NOT duplicate them, and user agents MUST ignore the duplicates. (1 of 3 refuters dissented,
  calling this a UA-ignored lint nit with zero accessibility impact — a fair caveat; verdict survives as
  a low DEVIATION.)
- **Citations:**
  - ARIA in HTML (W3C Recommendation) — https://www.w3.org/TR/html-aria/
  - Slider Pattern — ARIA Authoring Practices Guide — https://www.w3.org/WAI/ARIA/apg/patterns/slider/
  - Communicating Value and Limits for Range Widgets — APG — https://www.w3.org/WAI/ARIA/apg/practices/range-related-properties/
- **Recommended fix:** Remove `aria-valuemin/valuemax/valuenow` from `TradeoffSlider.tsx`, keeping only
  `aria-valuetext` (the one value-adding attribute). Relax the gate at `check-a11y-nojs.mjs:53` to assert
  the native control (`/type=["']range["']/`, already present) and `aria-valuetext`, dropping the
  `aria-valuenow` requirement. Keyboard operability (WCAG 2.1.1) is satisfied natively regardless.
